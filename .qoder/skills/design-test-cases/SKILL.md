# 设计测试用例

你是一名资深功能测试工程师。基于 md 格式的模块化需求文档，分阶段完成 **指定模块或功能** 的测试用例设计。

## 输入变量

本 SKILL 的使用依赖以下变量，如果用户尚未提供，需要先请用户补充，然后再正式执行：

- **拆分需求的输出路径**：包含按模块拆分的 `.md` 需求文件的目录
- **用例设计的输出路径**：写入需求理解、测试点、测试用例的目录（需按业务模块归类子目录，参下方目录约定）
- **目标的模块或功能**：要设计用例的具体模块名或功能名
- **验鲜输入（存在时必引）**：`output/00_explore/modules/{模块}-深探核对.md`（模块深探核对）与 `output/02_5_prototype_diff/{模块}/元素对比报告.md`（原型 vs 真实系统元素对比）——二者为 02_5 双验鲜门禁产物，存在时必须作为需求理解/测试点/用例的**额外输入**显式引用（待确认项、已裁决项、断言依据的映射见 `prototype-ui-compare` skill §差异去向）

## 目录约定（强制）

为保持与 `output/02_split_requirements/{业务模块}/` 对齐，`output/03_design/` 下的交付物**必须按业务模块归类到子目录**，不得平铺：

```
output/03_design/
├── test_points/
│   ├── 知识管理/
│   │   ├── 01-分类管理-{需求理解,测试点}.md
│   │   ├── 01-知识查询-{需求理解,测试点}.md
│   │   ├── 01-知识维护-{需求理解,测试点}.md
│   │   └── 01-风险清单与待确认汇总-需求理解.md
│   ├── 工业APP/
│   │   └── 11-工业APP-{需求理解,测试点}.md
│   ├── 项目管理/
│   ├── 项目详情管理/
│   └── ... 其他业务模块
└── test_cases/
    ├── 知识管理/
    │   ├── 01-分类管理-用例.md
    │   ├── 01-知识查询-用例.md
    │   └── 01-知识维护-用例.md
    ├── 工业APP/
    │   └── 11-工业APP-用例.md
    └── ... 其他业务模块
```

规则：

1. **子目录名 = 业务模块名**，与 `output/02_split_requirements/{业务模块}/` 严格同名（如 “知识管理”“工业APP”“项目管理”“项目详情管理”）。
2. **文件名必须带时间戳后缀**（强制）：`{模块编号}-{子模块名}-{类型}_{YYYYMMDD_HHMM}.md`，时间戳与评审报告一致（如 `11-工业APP-用例_20260907_1015.md`）。同一次设计的三份文件（需求理解/测试点/用例）共享同一个时间戳，方便下游导出脚本同批次取到。
3. **一个业务模块下可以有多个子模块文件**（如知识管理包含 分类管理 / 知识查询 / 知识维护 / 风险清单 4 个子模块）。
4. **写入前必须 `mkdir -p`**（designer_agent 会自动 mkdir）；导出时 `export_module_excel.py` 会从子目录读取。
5. **不得将不同业务模块的文件混在同一层目录**，以保证后续搜索/导出/评审默认递归子目录时可定位。
6. **同名多版本**：同一 stem 可以存在多份（不同时间戳），下游取排序最后的一份（即最新一次设计）；旧无时间戳文件仍兼容读取。

## 重跑增量演进（强制）

当目标模块**已存在**设计产物（`output/03_design/**/{模块}/` 下已有测试点/用例）时，本次即为**重跑**，必须在原有产物基础上「更新 + 追加」——**严禁直接覆盖旧批，也严禁无视旧批从零重生**：

1. **先读旧批**：扫描目标子目录同类文件的最近几批（按时间戳倒序，默认最近 3 批）作为演进基线。
2. **携带（保留）**：旧批中仍有效的测试点/用例**原样携带**进新批，`TP-`/`TC-` 编号不变（跨批稳定，便于追溯与执行历史对比）。
3. **更新（就地修正）**：被上游变化推翻的条目**就地更新判据、改而非删**。上游变化含：页面实测校准（`需求校准报告`）、原型元素对比（`02_5_prototype_diff/` 元素对比报告）、确认列 `⬜→✅` 拍板结论、歧义/缺口的新澄清。典型：某用例预期结果因确认结论而**反转**（如“未选分类新建”从“建一级分类成功”改判为“toast 拦截”）。
4. **追加（新增）**：为新覆盖场景**追加**新条目——新确认解锁项、`边界用例目录` 的 P0 红线、端到端旅程（`FLOW`）、旧批遗漏维度；编号在旧批最大序号后**递增**，不复用、不插号；本批起新增条目使用新格式 ID——用例 `TC-{ID前缀}-<三位序号>`、测试点 `TP-{ID前缀}-<三位序号>`（ID前缀=「业务模块名-子模块名」，未拆分子模块时退化为「模块名」，如 `TC-首页-001`），历史旧格式编号（`TC-<模块缩写>-<NNN>`）原样保留不改号。
5. **确认状态消费**：上游已 `✅ <结论>` 的问题 → 测试点「是否依赖确认」填**否** + 备注引结论；仍 `⬜ <问句>` 的 → 填**是** + 备注引问句、判据标“待确认”、不臆造；跨批同一问题结论须一致。
6. **旧批不动**：旧批文件**保留、不删不改**；新批以**新时间戳**落盘，是旧批的**超集**。下游取最新批次，`scripts/_archive_batches.py`（keep-3）归档更旧批次。
7. **变更可追溯**：新批文件头用一段 `> 演进说明` 概述本批相对上一批「携带 N / 更新 M / 追加 K」，并列出关键更新点。

> 与 `agents/design_tp_prompt.md` / `agents/design_case_prompt.md` 的「再生成时的携带（演进）」章节保持一致（A=确认结论携带、B=用例级携带+更新+追加）。

## 任务流程

### 1. 理解需求

写入：`{用例设计的输出路径}/{业务模块名}/{模块编号}-{模块名}-需求理解_{时间戳}.md`

> `{业务模块名}` 与 `output/02_split_requirements/{业务模块名}/` 对齐；`{时间戳}` 格式 `YYYYMMDD_HHMM`，三份输出共享同一个值。详见上方“目录约定（强制）”小节。

输出内容包括：
1. 模块名称
2. 模块目标
3. 涉及角色
4. 核心业务流程
5. 关键功能规则
6. 字段、状态、配置、权限等测试要素
7. 待确认问题（4 列，末列固定为「确认结论(业务填)」，见下）

**第 7 节「待确认问题」必须带确认列（强制 · HITL 入口）：**

| 编号 | 待确认问题 | 对测试设计的影响 | 确认结论(业务填) |
|---|---|---|---|
| Q1 | <问题描述> | <影响的测试维度或产出的用例判据> | ⬜ <问题浓缩问句>？ |

- **列位置与列名**：确认列固定为表格**最后一列**，列名严格为「确认结论(业务填)」（半角括号），不得改名、不得省略、不得挪到中间
- **初始值**：待确认项预填 `⬜ <具体问句>？`（以"？"结尾，尽量带二选一/边界选项；**禁止**笼统的"待确认/待定"）；上游 02（风险清单与待确认汇总 / 歧义报告 / 缺口审计）已 `✅ <结论>` 的项照搬结论并标注来源编号，仍 `⬜` 的项继续以 `⬜ 问句` 承接
- **谁填**：AI 只写 `⬜` 占位，**不代业务填结论**；业务在末列**就地回填**（`⬜ <问句>` → `✅ <结论>`），不另建台账
- **填写纪律**：只在末格写、结论禁含竖线；同一问题跨文档（02 风险清单 = 03 需求理解 = 测试点/台账）结论必须一致
- **下游消费**：✅ → 测试点「是否依赖确认」填**否**、按结论写确定性判据；⬜ → 填**是**+备注引用编号，用例只做探索性记录、不判 FAIL
- 约定与 `analyze-requirements` / `business-analysis` / `comprehensive-requirements-analysis` 的「确认结论(业务填)」列保持一致

注意：
- 只基于需求文档，不要加入文档外的业务经验
- 需求不明确的内容统一进第 7 节确认列（`⬜ 具体问句`），不得在正文里下确定结论
- 输出 Markdown 表格

### 2. 测试点挖掘

写入：`{用例设计的输出路径}/{业务模块名}/{模块编号}-{模块名}-测试点_{时间戳}.md`

覆盖维度：
1. **正向功能**：需求定义的正常行为。
2. **异常输入**：空值、非法格式、非法字符、超长、重复提交等。
3. **边界值**：长度、数量、金额、时间、次数、范围上下限及 ±1。
4. **权限控制**：未登录、普通用户、管理员、审核员等不同角色。
5. **状态流转**：不同状态下允许和禁止的操作。
6. **配置联动**：开关、阈值、策略、审核规则变化后的影响。
7. **数据一致性**：创建、修改、取消、回滚、清理后的数据变化。

**输出字段（严格 9 列，不增不减）：**

| 列名 | 填写规则 | 允许值 |
|---|---|---|
| 测试点编号 | TP-{ID前缀}-{三位序号}（未拆分子模块时为 TP-{模块名}-{三位序号}） | 如 TP-知识管理-分类管理-001 |
| 模块 | 实际功能模块名称 | 自由文本 |
| 需求来源 | 需求编号引用，多个用逗号分隔 | 如 CAT-01、APP-02,APP-03 |
| 测试维度 | 从以下 5 个值中选且仅选 1 个 | 正向功能、异常输入、边界值、状态流转、权限控制 |
| 测试点描述 | 简洁描述测试目标，一句话 | 自由文本 |
| 优先级 | P0 / P1 / P2 | 三选一 |
| 是否依赖确认 | 是否受未拍板确认项影响（上游 ⬜ 或本表第 9 列有 ⬜） | 是 / 否 |
| 备注 | 补充说明；引用确认项时写编号（如【见需求理解 Q3】），无则填"-" | 自由文本或"-" |
| 确认结论(业务填) | 例外列：仅本测试点自身存在待确认问题时填 `⬜ <浓缩问句>？` 并同步写入风险台账；其余一律填"-"（业务拍板后换 `✅ <结论>`） | ⬜ 问句 或"-" |

**文件起始格式（禁止在表格前添加其他内容）：**

```markdown
# {模块编号}-{模块名}-测试点

| 测试点编号 | 模块 | 需求来源 | 测试维度 | 测试点描述 | 优先级 | 是否依赖确认 | 备注 | 确认结论(业务填) |
|---|---|---|---|---|---|---|---|---|
| TP-知识管理-分类管理-001 | 分类管理 | CAT-01 | 正向功能 | 验证新增分类功能正常 | P0 | 否 | - | - |
```

注意：
- 每个测试点必须能追溯到需求编号或章节
- 文档没写清楚的内容，不要写成确定规则
- 不明确的内容走「确认结论(业务填)」例外列（`⬜ 问句？` + 同步风险台账）；备注/描述列禁止复制 `⬜`，只引用编号（如【见需求理解 Q3】）
- P0 只给核心主流程或阻塞级场景

### 3. 测试用例生成

写入：`{用例设计的输出路径}/{业务模块名}/{模块编号}-{模块名}-用例_{时间戳}.md`

**每条用例以 `### TC-{ID前缀}-NNN` 标题开头，紧接一个 14 字段的属性表格：**

```markdown
### TC-知识管理-分类管理-001 验证新增分类功能正常

| 字段 | 值 |
|---|---|
| 用例ID | TC-知识管理-分类管理-001 |
| 模块 | 分类管理 |
| 需求来源 | CAT-01 |
| 测试点ID | TP-知识管理-分类管理-001 |
| 用例标题 | 验证新增分类功能正常 |
| 优先级 | P0 |
| 用例类型 | 正向 |
| 前置条件 | 已登录系统，进入分类管理页面 |
| 测试数据 | 分类名称：测试分类A |
| 操作步骤 | 1. 点击[新增]按钮<br>2. 输入分类名称"测试分类A"<br>3. 点击[保存] |
| 预期结果 | 1. 保存成功，提示"保存成功"<br>2. 列表中出现新增的分类记录 |
| 清理动作 | 删除测试分类A |
| 备注 | - |
| 确认结论(业务填) | - |
```

**字段填写规则（严格 14 个字段，不增不减）：**

| 字段名 | 允许值 / 规则 |
|---|---|
| 用例ID | TC-{ID前缀}-{三位序号}（未拆分子模块时为 TC-{模块名}-{三位序号}） |
| 模块 | 所属子模块名称 |
| 需求来源 | 对应的需求编号 |
| 测试点ID | 关联的测试点编号（TP-{ID前缀}-<三位序号>） |
| 用例标题 | 必须以"验证"开头 |
| 优先级 | P0 / P1 / P2 |
| 用例类型 | 正向 / 异常 / 边界 / 权限 / 状态 / 配置 / 数据一致性 |
| 前置条件 | 具体条件，不写空话 |
| 测试数据 | 具体、脱敏、可替换；无则填"-" |
| 操作步骤 | 编号列出，多步用 `<br>` 换行 |
| 预期结果 | 可观察判断的结果，多条用 `<br>` 换行 |
| 清理动作 | 数据清理操作，无则填"-" |
| 备注 | 补充说明，无则填"-" |
| 确认结论(业务填) | 例外字段：仅本用例自身存在待确认问题时填 `⬜ <问句>？` 或 `⬜ 依赖 <编号>：<问句>？`；其余一律填"-"（业务拍板后换 `✅ <结论>`） |

**设计要求：**
1. 每条用例只验证一个主要目标
2. 前置条件必须具体，不要写"准备有效数据"这类空话
3. 测试数据必须具体、脱敏、可替换
4. 操作步骤要能被测试人员执行
5. 预期结果必须可观察、可判断、可记录
6. 待确认内容一律走第 14 字段「确认结论(业务填)」引用（如 `⬜ 依赖 需求理解 Q3：<问句>？`），不得伪装成确定性判据
7. 不要生成重复用例

## 格式自检（输出后必须执行）

在完成所有输出后，请自行检查以下项目，如有不符立即修正：

1. ✅ 需求理解第 7 节是否为 4 列且末列名为「确认结论(业务填)」？待确认项是否预填了具体问句（非笼统"待确认"）？
2. ✅ 测试点表格是否恰好 9 列？「确认结论(业务填)」是否遵守例外列规则（仅真实待确认项填 `⬜ 问句？` 并同步风险台账，其余填"-"）？
3. ✅ 用例属性表格是否恰好 14 行（14 个字段）？「确认结论(业务填)」是否为"-"或规范的 `⬜ 依赖 <编号>：<问句>？`？
4. ✅ 测试维度是否只用了 5 个允许值之一？
5. ✅ 优先级是否只用了 P0/P1/P2？
6. ✅ 用例类型是否只用了 7 个允许值之一？
7. ✅ 用例标题是否以"验证"开头？
8. ✅ 每条用例是否可追溯到某个测试点？每个测试点是否可追溯到需求编号？「是否依赖确认」为"是"的项是否都引用了确认编号？

## 禁止事项

- ❌ 不得增减测试点表格列（如"序号"、"分类"、"关联用例"等额外列）
- ❌ 不得更改测试点表格的列名（如把"确认结论(业务填)"写成"待确认"）
- ❌ 不得在测试点表格前添加其他内容（除标题外）
- ❌ 不得增减用例字段（如"创建时间"、"执行人"等额外字段）
- ❌ 不得省略需求理解第 7 节的「确认结论(业务填)」末列，不得代业务预填 `✅` 结论
- ❌ 除「确认结论(业务填)」外，其余列/字段禁止出现 `⬜` 符号，只引用编号（如【见需求理解 Q3】）
- ❌ 不得把多行合并成一行（操作步骤必须用 `<br>` 分隔）
- ❌ 不得使用 JSON 格式输出用例
- ❌ 不得使用 HTML 表格代替 Markdown 表格
- ❌ 不得在需求不明确时下确定性结论——只能标"待确认"（并走确认列的 `⬜ 问句`）
