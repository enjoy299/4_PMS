# 业务梳理（Business Analysis）

## 在流水线中的位置

```
系统探索(explore-web-system) → 【业务梳理(business-analysis)】 → 需求拆分(analyze-requirements)
                                   ↓ 输出                          → 需求理解 → 测试点 → 用例设计 → 评审 → 执行
                          output/01_business/{模块}-业务全景图.md
```

本阶段是**独立的一步**，与系统探索、用例设计等平级。它把探索得到的"页面实际是什么样"和需求写的"应该是什么样"做一次**双向对齐**，产出稳定的业务基线，供下游消费。

## 角色定位

你是一名**资深业务分析师（BA）+ 测试分析师**。核心信条：

> **"页面事实和需求文字打架的地方，正是缺陷和测试机会的富矿。"**

## 何时使用

- 完成系统探索后，需要把碎片化的页面事实沉淀为结构化业务认知
- 需求文档与真实系统可能存在出入，需要先对齐再进入测试设计
- 需要一份"角色/实体/流程/术语"的全局视图，作为多人协作的共识基线

**何时不使用**：已经只关心测试点/用例时，直接用 `analyze-requirements` / `design-test-cases`；本阶段**不产出测试点和用例**。

## 输入

1. **原始需求文档**：`inputs/requirements/{n}、{模块}.md`
2. **系统探索产物（页面事实）**：
   - `output/00_explore/{模块}-功能地图.md`、`output/00_explore/*-{模块}-探索记录.md`
   - `output/02_split_requirements/{模块}/*基于页面探索*.md`（需求校准报告）
   - 若无探索产物，退化为"仅基于需求文档梳理"，并在第 7 节注明未做页面比对

## 输出

单个文件：`output/01_business/{模块}-业务全景图.md`（8 个小节，见下）

## 业务全景图标准结构（8 节）

| 节 | 名称 | 内容 | 必填 |
|---|---|---|---|
| 1 | 系统概览 | 业务目标、范围、在整体系统中的位置 | 是 |
| 2 | 角色与权限矩阵 | 角色 / 职责 / 可见范围 / 可执行操作 / 证据来源 | ✅ |
| 3 | 功能清单 | **稳定功能ID（BA-xx-nn）** / 功能点 / 简述 / 涉及角色 / 证据等级 | ✅ |
| 4 | 业务实体、数据流与模块依赖 | 实体ER(1:1/1:N/N:N) + 数据流(谁产生→谁消费) + 模块依赖方向 + 循环依赖检查 | ✅ |
| 5 | 关键业务流程与状态 | 单模块流程 + **跨模块端到端链路(泳道)** + 状态机(枚举/合法流转/由哪些模块改变) | ✅ |
| 6 | 领域术语表 | 术语 / 含义 / 易混词 / 来源 | 是 |
| 7 | 需求缺口与实现差异 | 探索 vs 需求 的双向比对结果 + **确认结论(业务填)列** | ✅ |
| 8 | 待确认问题 | 问题 / 影响环节 / 建议确认对象 / **确认结论(业务填)列** | 是 |

### 第 7/8 节「确认结论(业务填)」列约定（待业务回填）

凡产出含待确认内容的业务全景图，第 7 节与第 8 节表格**必须**在末尾加一列「确认结论(业务填)」，格式统一：

| 要素 | 约定 |
|---|---|
| 列位置 | 表格最后一列，列名「确认结论(业务填)」 |
| 初始值·🔴/⚠️ | `⬜ <具体问句>`（必须预填“要拍板什么”） |
| 初始值·🟡🟢 | 纯 `⬜` 占位；若该缺口值得拍板可保留 `⬜ <问句>`（问句优先于空占位） |
| 问句要求 | 直接抛出具体问题，带二选一/边界选项、以“？”结尾；**禁止**填笼统的“待确认/待定” |
| 问句来源 | 第 7 节 = 该缺口/冲突/异常需拍板的核心；第 8 节 = 「问题」列的浓缩版 |
| 确认后 | 业务填完把 `⬜` 换 `✅ <结论>`（结论 + 依据/范围） |
| 风格对齐 | 与 `analyze-requirements` / `comprehensive-requirements-analysis` 的 HITL 确认列约定一致 |

> 目的：让产品/开发在回填前一眼看清“被问的是什么”，回填时只需作答，无需反推问题。

## 关联关系梳理方法（第 4、5 节展开）

梳理“模块关联”用 6 个视角，从静态到动态，每条关联都要标出**交接点**与**依赖方向**：

| 视角 | 方法/图 | 回答什么 | 落到哪节 |
|---|---|---|---|
| 实体关系 | ER（1:1 / 1:N / N:N） | 各模块是否操作同一批业务对象、主子从属 | 4.1 |
| 数据流 | DFD（谁产生 → 谁消费） | 数据在模块间如何流动 | 4.2 |
| 集成/依赖 | 依赖表 + 方向 + **循环依赖检查** | 谁调用谁、测 A 是否必须先有 B | 4.3 |
| 跨模块流程 | 泳道图 / BPMN | 一条流程横跨哪些模块与角色、交接点在哪 | 5.2 |
| 状态流转 | 状态机 | 实体状态被哪些模块改变、合法流转链 | 5.3 |
| 关键路径 | 依赖拓扑 | 哪些模块是命脉、决定测试与回归优先级 | 4.3 / 5.2 |

### 可追溯桥接（供下游 design-test-cases，本阶段不产出用例）

给功能/实体/链路赋**稳定 ID**（`BA-<模块>-<nn>` / `ENT-<模块>-<nn>` / `FLOW-<模块>-<nn>`），下游据此建“业务要素 → 用例”可追溯矩阵。业务要素与测试手段的对应关系（仅梳理锚点，非测试结论）：

| 梳理产物 | 下游通常验证 |
|---|---|
| 实体关系(1:N/N:N) | 数据一致性（主记录删/改时子记录处理） |
| 数据流 / 模块依赖 | 集成测试、接口契约一致性 |
| 跨模块端到端链路 | 完整业务旅程（用户动作 → 最终可见状态，非单跳） |
| 状态机 | 合法流转 + 非法流转拦截 |

> 本 skill 只梳理并标注上述锚点，**不写测试点、不设计用例**（遵守核心原则 1）。

## 核心原则

### 1. 只梳理、不下测试结论
本阶段只建立业务事实与结构，**不生成测试点、不写用例**。测试维度交给 `design-test-cases`。

### 2. 页面事实优先（Evidence 冲突处理）
| 情况 | 归类 | 处理 |
|---|---|---|
| 页面有、需求没写 | **需求缺口** | 记入第 7 节，标严重度 |
| 需求写了、页面没有/不符 | **实现差异** | 记入第 7 节（往往是高价值测试点） |
| 两者都有但表述不一致 | **歧义 / 冲突** | 记入第 7、8 节 |
| 两者都没有 | **待确认** | 记入第 8 节，不臆造 |

### 3. 证据等级（E0–E3，禁 E4）
每条关键结论标注来源与证据等级：E0 原文明确 / E1 可直接推断 / E2 行业惯例 / E3 类似系统经验。**E4 无依据猜测禁止出现**，只能转为"待确认"。

## 操作方式（两种）

### A. 框架命令（推荐，走 Qoder 桥接）
```bash
python run.py business 首页          # 单模块
python run.py business               # 所有模块
# 或独立脚本
python scripts/run_business.py 知识管理
```
脚本生成提示词并复制到剪贴板 → 粘贴到 Qoder 对话 → Qoder 直接写出 `output/01_business/{模块}-业务全景图.md`。

### B. Qoder 对话直接执行
让 Qoder 读取本 skill + 需求文件 + 探索产物，按上面 8 节结构产出业务全景图。
