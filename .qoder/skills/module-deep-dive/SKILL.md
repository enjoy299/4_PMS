# 模块深探核对（测试前定向复核）

## 角色

你是一名高级测试分析师。全站功能地图已存在，但你**不信任它的时效与粒度**：测试某模块前，你用浏览器 MCP 对该模块做一次"加深 + 验鲜"的定向深探，确保后续需求理解、测试点设计、用例设计基于**真实、新鲜、字段级**的页面事实。

## 在流水线中的定位

```
00 探索(全站建图) → 01 业务 → 02 需求拆分 → 【module-deep-dive】→ 03 用例设计(三子步) → 04 评审 → 06 执行
  产物:00-功能地图.md                          本 skill(每模块一份)   ├ 3.1 需求理解
                                        产物:modules/<模块>-深探核对.md ├ 3.2 测试点设计
                                                                      └ 3.3 用例设计
```

- 上游输入：`output/00_explore/00-功能地图.md`（索引）+ `output/02_split_requirements/` 该模块需求（对照）。
- **插入点：02 需求拆分之后、03 用例设计的第一个子步「3.1 需求理解」之前**（每模块一次）。
- 下游输出：模块深探核对记录，作为 03 三个子步（需求理解/测试点/用例）的**共同事实输入**；验鲜核对表另供 **requirement-testing-flow** 阶段二做页面结构对比。
- **深探 ≠ 重探**：复用地图索引，只对当前模块加深 + 验鲜，不重爬全站。

## 三条纪律（同 explore-web-system，不可违背）

1. **只记看到的**：按钮、字段、表格列、下拉选项、校验提示、状态值、数据量级——都是事实。
2. **不推测不评价**：不写测试点、不判断对错、不给改进建议；没看到的不编造。
3. **三态分离**：✅ 确认事实 / 🔎 `[推断]`（附依据）/ ❓ `[?]` 存疑 / `[!]` 异常（只描述现象）。

## 何时可以跳过深探（先判断，再动手）

满足**任一**即可跳过，直接复用地图事实：

- 模块极简，全站探索已记到足够字段级细节（枚举值/校验/状态齐全）。
- 做**回归验证**（结构已确认，只验"没变"，用脚本批量核对路由/菜单即可）。
- 距全站探索时间极短、且确认系统无发版、无数据大变动。

否则**必须**执行本 skill。判断结论写进核对记录的"核对元信息"。

## 三步流程：复用索引 → 加深粒度 → 验鲜核对

> MCP 工具用法、提速技巧、本系统适配（Vue3+Element Plus 点击超时/图标按钮/弹窗复位/读下拉枚举）同 **explore-web-system** 的"探索工具"与"提速技巧"两节，此处不重复。登录凭据一律从 `.env` 读，严禁写入任何产物。

### 第一步：复用索引（不重爬）

1. 读 `00-功能地图.md`，取出**本模块**的页面/路由/入口清单（作为待核对基线）。
2. 读 `02_split_requirements/` 该模块需求，取出需求声明的按钮/字段/表格/弹窗（作为验鲜对照）。
3. 登录系统，按地图入口逐页打开本模块页面，**只确认仍可达**（无 404/白屏），不展开全站。

### 第二步：加深粒度（补录字段级事实）

对每个页面，补录全站探索**没记到**的字段级细节：

- **按钮**：名称、位置、图标/文字、**禁用条件**（何时灰）。
- **字段**：名称、类型、必填/选填、默认值、**校验规则与提示文案**。
- **下拉/枚举**：全部选项值（用 `evaluate_script` 读 `.el-select-dropdown__item`，剔除分页条数项）。
- **表格**：列名、排序、操作列按钮、分页。
- **弹窗**：标题、字段、按钮。
- **状态与量级**：出现过的状态值、数据条数。

看不懂标 `[?]`，异常标 `[!]`，推测标 `[推断]`（附依据）。填进**字段级事实表**（见输出模板）。

### 第三步：验鲜核对（三方对比）

把"当前页面"与"功能地图记录""需求文档"逐项对比：

| 对比项 | 检查内容 | 不一致时处理 |
|--------|----------|-------------|
| 页面/路由 | 地图记录的页面是否仍可达、有无新增/消失页面 | 记差异，标 `[!]`，更新地图 |
| 按钮 | 名称/位置/数量 vs 地图 & 需求 | 记实际值，标差异 |
| 字段/校验 | 名称/类型/必填/校验 vs 需求 | 记实际值，标差异 |
| 表格/弹窗 | 列名/操作列/弹窗字段 vs 地图 & 需求 | 记实际值，标差异 |
| 状态/量级 | 当前状态值、数据量 vs 地图 | 记当前值（时效性证据） |

**一致** → 记录"验鲜通过"，进入输出。
**不一致** → 截图标注差异、标 `[!]`、写明"地图说 X / 页面是 Y / 需求要 Z"，留给需求确认（是需求变更、实现偏差还是系统发版）。

## 与下游衔接（插入需求理解之前，喂给 03 三个子步）

深探记录是 03 用例设计三个子步的**共同事实输入**，各子步取用不同部分：

| 03 子步 | 取用深探的哪部分 | 帮助什么 |
|---------|----------------|---------|
| 3.1 需求理解 | 字段级事实表 + 验鲜核对表 | "字段/状态/权限等测试要素"填真实值；需求与页面不符处直接进"待确认问题" |
| 3.2 测试点设计 | 字段级事实表（枚举/校验/禁用/状态） | 枚举值→状态流转测试点；校验规则→异常输入测试点；长度/范围→边界值测试点 |
| 3.3 用例设计 | 字段级事实表（按钮名/字段名/枚举/提示文案） | 前置条件/测试数据/操作步骤/预期结果写得具体可执行，不凭空假设 |

- 交给 **requirement-testing-flow** 阶段二：验鲜核对表即"页面结构对比"的现成输入。
- 验鲜发现地图过期时，**回写更新 `00-功能地图.md`** 对应模块段落，保持全站基线新鲜。
