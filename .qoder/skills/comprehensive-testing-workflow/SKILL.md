# 端到端功能测试工作流（Comprehensive Testing Workflow）

> **设计灵感来源**：
> - [testomat.io STLC Guide](https://testomat.io/blog/software-testing-life-cycle-guide/) — STLC 六阶段标准（入口/出口准则）
> - [fishzjp/qa-skills](https://github.com/fishzjp/qa-skills) — 10 技能 QA 流水线、文件即状态、人工裁决检查点
> - [vostride/agent-qa](https://github.com/vostride/agent-qa) — 故障分流(result-triage)、debug-fix 最小修复
> - [naodeng/awesome-qa-skills](https://github.com/naodeng/awesome-qa-skills) — 测试策略、功能测试、探索式测试工作流
> - [softaworks/agent-toolkit](https://github.com/softaworks/agent-toolkit) — 回归套件分层（Smoke/Targeted/Full）
> - [github/awesome-copilot](https://github.com/github/awesome-copilot) — ISTQB 测试过程活动

## 角色定位

你是一名**资深 Web 功能测试工程师 + 测试流程架构师**，负责组织和执行从需求分析到测试收尾的完整测试生命周期。

## 何时使用

- 拿到一个新功能模块，需要从零开始组织测试工作
- 需要安排测试执行的优先级和顺序
- 测试执行中发现 Bug，需要标准化报告和跟踪
- 一轮测试完成后需要做回归测试
- 测试周期结束需要输出收尾报告和经验总结

**何时不使用**：仅需要分析需求或用例设计时，使用 `analyze-requirements` 或 `comprehensive-test-case-design`。

## 八阶段测试工作流（STLC 增强版）

基于 ISTQB 标准 STLC 六阶段，增加冒烟验证和回归测试两个实战阶段：

```
Phase 1: 准入检查（Entry Gate）          ← 新增
   ↓
Phase 2: 测试计划（Test Planning）        ← STLC Phase 2
   ↓
Phase 3: 环境准备与冒烟（Setup & Smoke）  ← 合并 STLC Phase 4 + 新增冒烟
   ↓
Phase 4: 测试执行（Test Execution）       ← STLC Phase 5
   ↓
Phase 5: Bug 报告与跟踪（Defect Mgmt）   ← 新增
   ↓
Phase 6: 回归测试（Regression）           ← 新增
   ↓
Phase 7: 探索式测试（Exploratory）        ← 新增
   ↓
Phase 8: 测试收尾（Test Closure）         ← STLC Phase 6
```

**核心原则**（来自 fishzjp/qa-skills）：
- **文件即状态** —— 每个阶段的产出存为文件，下一阶段只读文件，不怕中断
- **关键决策人拍板** —— 阻塞级 Bug 定性、是否发版，由人裁决，Agent 只提案
- **先验证再测试** —— 页面结构与需求一致后才开始功能测试

### Phase 1: 准入检查（Entry Gate）

**目标**：确认测试前提条件满足，避免在不具备条件的情况下开始测试。

**准入检查清单**：

| # | 检查项 | 通过标准 | 阻塞时处理 |
|---|---|---|---|
| 1 | 需求文档就绪 | 有经评审的需求文档或 PRD | 拒绝测试，等需求 |
| 2 | 需求分析完成 | 已有拆分后的模块需求文件 | 先执行 analyze-requirements |
| 3 | 测试用例就绪 | 有用例文件且通过评审 | 先执行 design-test-cases |
| 4 | 测试环境可用 | 可登录目标系统，页面可访问 | 联系运维/开发 |
| 5 | 测试数据准备 | 有满足前置条件的测试账号和数据 | 准备测试数据 |
| 6 | 代码已部署 | 目标版本已部署到测试环境 | 等待部署完成 |

**输出**：`准入检查报告.md`

```markdown
## 准入检查报告

| 检查项 | 状态 | 备注 |
|---|---|---|
| 需求文档 | ✅ 就绪 | output/02_split_requirements/ 已有 |
| 测试用例 | ✅ 就绪 | 共 N 条用例 |
| 测试环境 | ✅ 可用 | {环境地址} |
| 测试数据 | ⚠️ 部分 | 需补充 XX 角色的测试账号 |

**准入结论**：✅ 可开始测试 / ❌ 阻塞（原因）
```

### Phase 2: 测试计划（Test Planning）

**目标**：确定测试范围、优先级、策略和资源安排。

**测试计划模板**：

```markdown
## 测试计划：{模块名称}

### 1. 测试范围
- **纳入测试**：{列出要测的功能模块}
- **排除测试**：{列出不测的功能及原因}

### 2. 测试策略
| 测试类型 | 是否纳入 | 深度 | 说明 |
|---|---|---|---|
| 功能测试 | ✅ | 全量 | 所有 P0/P1 用例 |
| 边界测试 | ✅ | 全量 | 关键输入边界 |
| 权限测试 | ✅ | 全量 | 所有角色验证 |
| 兼容性测试 | ⚠️ | 抽样 | 仅 Chrome + Firefox |
| 性能测试 | ❌ | 不测 | 本轮不涉及 |

### 3. 执行顺序
按模块依赖和风险排序：
1. {核心模块}（P0，阻塞其他模块）
2. {重要模块}（P1）
3. {一般模块}（P2）

### 4. 资源与时间
| 阶段 | 预计时间 | 负责人 |
|---|---|---|
| 冒烟测试 | 0.5 天 | |
| 功能测试 | N 天 | |
| 回归测试 | 1 天 | |
| 测试收尾 | 0.5 天 | |

### 5. 风险与应对
| 风险 | 影响 | 应对措施 |
|---|---|---|
```

### Phase 3: 环境准备与冒烟测试（Setup & Smoke）

**目标**：确认测试环境就绪，核心流程可走通。

#### 3.1 环境准备

- 确认测试环境地址和版本
- 准备测试账号（各角色至少一个）
- 准备测试数据（基础数据、配置项）
- 确认浏览器版本（建议 Chrome 最新版为主）

#### 3.2 冒烟测试（Smoke Test）

**目的**：用最少用例验证核心流程是否可测。15–30 分钟内完成。

**冒烟用例选取原则**：
- 只选 P0 用例中的主流程
- 每个核心功能选 1–2 条正向用例
- 总用例数控制在 10–20 条

**冒烟结果处理**：

| 冒烟结果 | 处理 |
|---|---|
| ✅ 全部通过 | 进入 Phase 4 正式测试 |
| ⚠️ 部分失败 | 记录失败项，联系开发修复后重跑冒烟 |
| ❌ 大面积失败 | **阻塞测试**，退回开发，出具阻塞报告 |

**输出**：`冒烟测试报告.md`

```markdown
## 冒烟测试报告

| 用例ID | 用例标题 | 结果 | 备注 |
|---|---|---|---|
| TC-知识管理-分类管理-001 | 验证新增XX功能 | ✅ PASS | |
| TC-知识管理-分类管理-002 | 验证XX列表加载 | ❌ FAIL | 页面白屏，已报 Bug |

**冒烟结论**：✅ 通过 / ❌ 阻塞（原因）
```

### Phase 4: 测试执行（Test Execution）

**目标**：按照计划和用例，系统化执行功能测试。

#### 4.1 执行顺序（来自 requirement-testing-flow 的实战顺序）

```
从左到右 → 从上到下 → 从外到里

顶部工具栏（筛选/搜索/批量）  ← 先测
    ↓
左侧树/导航                  ← 次测
    ↓
右侧列表/表格                ← 再测
    ↓
行内操作按钮                 ← 后测
    ↓
弹窗/详情页                  ← 最后测
```

#### 4.2 每轮执行规范

**每条用例执行后记录**：

| 字段 | 填写规则 |
|---|---|
| 执行结果 | PASS / FAIL / BLOCK / SKIP |
| 实际结果 | 与预期不符时必填 |
| 截图 | FAIL 时必截，标注问题位置 |
| 浏览器 | 记录浏览器和版本 |
| 备注 | 环境异常、数据问题等 |

**结果状态定义**：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| ✅ PASS | 实际结果与预期一致 | 标记通过 |
| ❌ FAIL | 实际结果与预期不符 | 提 Bug → Phase 5 |
| 🚫 BLOCK | 被其他问题阻塞无法执行 | 记录阻塞原因，后续补测 |
| ⏭️ SKIP | 本轮不测（低优先级/环境限制） | 记录跳过原因 |

#### 4.3 执行中的注意事项

- **一条用例只验证一个目标** —— 发现多个问题分多条 Bug 提
- **先提 Bug 再执行下一条** —— 不要积压 Bug 不报
- **BLOCK 用例及时跟进** —— 每天检查阻塞项是否解除
- **不确定的结果不要标 PASS** —— 标 BLOCK 并备注"需确认"

### Phase 5: Bug 报告与跟踪（Defect Management）

**目标**：标准化 Bug 报告，确保开发可复现、可修复。

#### 5.1 Bug 报告模板

```markdown
### BUG-{模块缩写}-{序号} {简短标题}

| 字段 | 值 |
|---|---|
| Bug ID | BUG-{模块}-{序号} |
| 关联用例 | TC-{ID前缀}-{三位序号} |
| 标题 | {功能}在{条件}下{现象} |
| 严重程度 | 阻塞(S1) / 严重(S2) / 一般(S3) / 建议(S4) |
| 优先级 | 紧急(P1) / 高(P2) / 中(P3) / 低(P4) |
| 环境 | {环境地址} / {浏览器+版本} / {操作系统} |
| 前置条件 | {账号/数据/状态} |
| 复现步骤 | 1. {步骤1}<br>2. {步骤2}<br>3. {步骤3} |
| 预期结果 | {应该发生什么} |
| 实际结果 | {实际发生了什么} |
| 截图/日志 | {截图路径或控制台日志} |
| 复现概率 | 必现 / 偶现(N/10) |
| 备注 | {补充信息} |
```

#### 5.2 严重程度判定标准

| 等级 | 定义 | 示例 |
|---|---|---|
| S1 阻塞 | 核心流程不可用，无绕过方案 | 登录失败、页面白屏、数据丢失 |
| S2 严重 | 核心功能异常，有绕过方案 | 新增报错但编辑可用、金额计算错误 |
| S3 一般 | 非核心功能异常或 UI 问题 | 筛选条件失效、排序不对、样式错位 |
| S4 建议 | 体验优化、文案错误 | 提示语不友好、按钮对齐偏差 |

#### 5.3 Bug 生命周期

```
新建(NEW) → 已确认(CONFIRMED) → 修复中(FIXING) → 已修复(FIXED)
   ↓                                                    ↓
驳回(REJECTED)                                    回归验证
   ↓                                              ↓        ↓
已关闭                                         PASS    FAIL → 重开(REOPEN)
```

#### 5.4 Bug 分流决策（来自 vostride/agent-qa result-triage）

发现 Bug 后先做分流判断：

| 分流类型 | 判断依据 | 处理 |
|---|---|---|
| 产品 Bug | 功能行为与需求不符 | 提 Bug 给开发 |
| 需求歧义 | 需求描述不清导致理解差异 | 回退给产品确认 |
| 环境问题 | 仅特定环境出现 | 记录环境信息，联系运维 |
| 数据问题 | 测试数据导致的异常 | 更换数据重测 |
| 已知问题 | 已在 Bug 库中记录 | 关联已有 Bug，不重复提 |

### Phase 6: 回归测试（Regression Testing）

**目标**：验证 Bug 修复有效且未引入新问题。

#### 6.1 回归套件分层（来自 softaworks/agent-toolkit）

| 层级 | 范围 | 执行时间 | 触发时机 |
|---|---|---|---|
| **冒烟回归** | 核心主流程 P0 用例 | 15–30 分钟 | 每次发版后 |
| **定向回归** | Bug 所在模块 + 关联模块 | 30–60 分钟 | Bug 修复后 |
| **全量回归** | 所有 P0+P1 用例 | 2–4 小时 | 重大版本发布前 |

#### 6.2 回归范围确定

**Bug 修复后的影响面分析**：

```
修复的 Bug
│
├── 直接影响：Bug 所在功能 → 必测
├── 间接影响：共享数据/组件的关联功能 → 必测
├── 全局影响：公共模块(登录/权限/导航) → 冒烟回归
└── 无影响：完全独立的功能 → 可跳过
```

#### 6.3 回归执行规范

1. **先验证 Bug 本身** —— 按原 Bug 的复现步骤验证已修复
2. **再验证关联功能** —— 同模块的 CRUD 和状态流转
3. **最后冒烟核心流程** —— 确保全局不受影响
4. **回归结果记录** —— 每条用例标记 PASS/FAIL + 关联 Bug ID

### Phase 7: 探索式测试（Exploratory Testing）

**目标**：在结构化用例之外，发现未覆盖的缺陷。

#### 7.1 何时做探索式测试

- 结构化用例执行完成后
- 时间充裕时（至少预留 1–2 小时）
- 新功能、复杂功能、高风险功能

#### 7.2 Charter 驱动方法（来自 fishzjp/exploratory-testing）

每次探索式测试前定义 Charter：

```markdown
## 探索式测试 Charter

- **目标**：{要探索的功能或场景}
- **时间盒**：{30–90 分钟}
- **关注点**：{边界、权限、并发、异常输入…}
- **不做**：{明确排除的范围}
```

#### 7.3 探索式测试常见策略

| 策略 | 方法 | 示例 |
|---|---|---|
| 错误推测 | 根据经验猜测易错点 | 表单重复提交、emoji 文件名 |
| 极端数据 | 超大/超小/空/特殊字符 | 输入 10000 字符的备注 |
| 快速操作 | 连续点击、快速切换 | 快速切换筛选条件 |
| 权限穿越 | 用不同角色做同一操作 | 普通用户访问管理功能 |
| 中断恢复 | 操作中途中断再恢复 | 表单填写中途刷新页面 |
| 并发操作 | 多窗口/多标签同时操作 | 两个窗口同时编辑同一条数据 |

#### 7.4 探索式测试记录

```markdown
## 探索式测试记录

| # | 时间 | 操作 | 发现 | 严重性 | 是否转Bug |
|---|---|---|---|---|---|
| 1 | 14:30 | 快速双击删除按钮 | 弹出两个确认框 | S3 | ✅ BUG-XX-005 |
| 2 | 14:45 | 输入 emoji 到名称字段 | 保存成功但列表显示乱码 | S2 | ✅ BUG-XX-006 |
```

### Phase 8: 测试收尾（Test Closure）

**目标**：汇总测试结果，输出测试报告，总结经验教训。

#### 8.1 测试收尾报告

```markdown
## 测试收尾报告：{模块名称} {版本号}

### 1. 测试概要
| 项目 | 数据 |
|---|---|
| 测试周期 | {开始日期} ~ {结束日期} |
| 测试环境 | {环境地址} / {浏览器} |
| 用例总数 | N |
| 执行数 | N |
| 通过数 | N (XX%) |
| 失败数 | N (XX%) |
| 阻塞数 | N (XX%) |
| 跳过数 | N (XX%) |

### 2. Bug 统计
| 严重程度 | 发现数 | 已修复 | 遗留 |
|---|---|---|---|
| S1 阻塞 | N | N | N |
| S2 严重 | N | N | N |
| S3 一般 | N | N | N |
| S4 建议 | N | N | N |
| **合计** | **N** | **N** | **N** |

### 3. 遗留风险评估
| 编号 | 遗留项 | 风险等级 | 建议 |
|---|---|---|---|

### 4. 发版建议
- ✅ 建议发版（无 S1/S2 遗留）
- ⚠️ 有条件发版（有 S2 遗留但可接受，需注明风险）

### 5. 经验教训

```

## 阶段间流转规则

```
准入检查 ──✅──→ 测试计划 ──→ 环境+冒烟 ──✅──→ 测试执行
   ❌              │                ❌              │
   ↓               │                ↓               │
 阻塞,退回       │            阻塞,退回          │
                   │                               ↓
                   │                         Bug 报告
                   │                               ↓
                   │                         回归测试 ←──Bug修复后
                   │                               ↓
                   │                         探索式测试
                   │                               ↓
                   └────────────────────→ 测试收尾 ──→ 归档
```

**流转铁律**（来自 fishzjp/qa-skills）：
1. 冒烟不通过 → **禁止进入正式测试**
2. S1 Bug 未修复 → **禁止发版**
3. 回归不通过 → **禁止上线**
4. 所有检查点的阻塞/放行决定 → **由人拍板，Agent 只提案**

## 常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| "跳过冒烟直接全测" | 核心流程不通浪费时间 | 15 分钟冒烟确认可测性 |
| "积压 Bug 不报" | 忘记细节，开发无法复现 | 发现即报，一条 Bug 一个问题 |
| "Bug 修复后只测 Bug 本身" | 关联功能回归出新 Bug | 按影响面分析做定向回归 |
| "按 deadline 关闭测试" | 遗留严重缺陷上线 | 按质量标准关闭，不按时间 |
| "只看通过率不看风险" | 95% 通过但核心功能全挂 | 关注 P0 通过率和 S1/S2 遗留数 |
| "不做探索式测试" | 结构化用例之外的缺陷漏测 | 至少为高风险功能做一次 Charter 探索 |
