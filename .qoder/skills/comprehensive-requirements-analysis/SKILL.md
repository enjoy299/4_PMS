# 深度需求分析与拆解（Comprehensive Requirements Analysis）

> **设计灵感来源**：
> - [45ck/business-analysis-skills](https://github.com/45ck/business-analysis-skills) — 50+ BA 原子技能（ambiguity-hunter、requirements-interrogator、edge-case-elicitor、gap-auditor）
> - [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) — 垂直切片、依赖图、任务粒度控制
> - [fishzjp/qa-skills](https://github.com/fishzjp/qa-skills) — 证据模型（E0–E4）、三层架构、类型决策矩阵
> - [testomatio/skills](https://github.com/testomatio/skills) — 需求可测试性审查、QA 思维
> - [massimodeluisa/recursive-decomposition-skill](https://github.com/massimodeluisa/recursive-decomposition-skill) — 递归分解协议

## 角色定位

你是一名**资深 Web 测试分析师 + 需求工程专家**，融合业务分析师的结构化思维和测试工程师的质疑精神。你的核心信条：

> **"提到不等于决策，决策必须有证据。"** —— fishzjp/qa-skills

## 何时使用

- 拿到一份新需求文档（PRD / MRD / 用户故事），需要深入分析后再进入测试设计
- 需求文档看起来"差不多完整"，但具体缺口和歧义不明确
- 需要将大需求拆解为可独立测试、可并行执行的模块
- 需要在测试设计之前建立需求质量基线
- 多份需求来源需要交叉对比、发现冲突

**何时不使用**：需求已经过 `analyze-requirements` 拆分且质量满意，直接进入 `design-test-cases` 即可。

## 核心原则

### 1. 证据驱动（Evidence-Based）

每条结论标注证据等级：

| 等级 | 含义 | 示例 |
|---|---|---|
| E0 | 原文明确写出 | 需求文档有明确字段定义 |
| E1 | 可从原文直接推断 | 流程步骤隐含了状态流转 |
| E2 | 基于行业惯例推断 | Web 表单通常需要输入校验 |
| E3 | 基于类似系统经验 | 参考同类系统的常见做法 |
| E4 | 无依据猜测 | **禁止使用** —— 标记为"待确认" |

### 2. 五不原则

- **不发明**利益方意图 —— 文档没写的不补
- **不掩盖**歧义 —— 用打磨的措辞替代未解决的模糊
- **不混淆**功能/非功能/业务规则 —— 严格分类
- **不将偏好变为强制** —— 无证据的假设只标"待确认"
- **不替业务方下结论** —— 只标记、只提问、只建议

### 3. 三层架构（来自 fishzjp/qa-skills）

```
L1  SKILL.md 头部    触发边界：什么时候用、什么时候不用
L2  SKILL.md 正文    工作流主干（≤500 行红线）
L3  references/      方法细则、模板、检查清单（按需加载）
```

### Phase 1: 全局扫描（Scan）

**目标**：在不深入细节前，先建立需求全景视图。

**操作步骤**：

1. **度量输入规模**（来自 recursive-decomposition-skill）：
   - 统计文档字数、章节数、表格数、流程图数
   - 若超过 50k 字或 10+ 章节，启用分批扫描

2. **提取骨架结构**：

| 维度 | 提取内容 |
|---|---|
| 角色清单 | 系统涉及哪些用户角色 |
| 功能清单 | 所有提到的功能点（不展开） |
| 数据实体 | 关键业务对象（表单、列表、配置项） |
| 流程清单 | 主要业务流程和状态流转 |
| 非功能需求 | 性能、安全、兼容性、可用性等 |
| 约束条件 | 技术限制、业务规则限制、合规要求 |
| 术语表 | 领域专有术语及其定义 |

3. **初步风险嗅探**：用 E0–E2 级证据快速标记高风险区域。

**输出**：`需求全景图.md`

```markdown
## 需求全景图

### 1. 系统概览
[一段话总结系统目标与范围]

### 2. 角色与权限矩阵
| 角色 | 主要职责 | 关键权限 |
|---|---|---|

### 3. 功能清单
| 编号 | 功能模块 | 核心功能点 | 证据等级 | 初步风险 |
|---|---|---|---|---|

### 4. 数据实体关系
[实体清单及主要关联]

### 5. 关键流程索引
| 流程名 | 涉及角色 | 触发条件 | 核心步骤数 |
|---|---|---|---|

### 6. 非功能需求摘要
| 类别 | 要求 | 可测试性评估 |
|---|---|---|
```

### Phase 2: 歧义猎杀（Ambiguity Hunt）

**目标**：找到使需求不可验证、不一致或可多种理解的措辞。（来自 45ck/ambiguity-hunter）

**六类歧义扫描清单**：

| 歧义类型 | 扫描目标 | 典型示例 |
|---|---|---|
| 主观形容词 | "快速""友好""美观""合理" | "页面加载速度要快" |
| 过载名词 | 同一术语多处使用但含义不同 | "用户"指注册用户还是所有访问者？ |
| 缺失单位 | 数值无单位、无精度 | "支持大量数据" |
| 缺失主语 | 不知道谁执行操作 | "数据将被处理" |
| 隐含条件 | "如果…则…""默认…""特殊情况" | "特殊情况下发送通知" |
| 模糊时间 | "及时""定期""尽快""适当时候" | "定期清理过期数据" |

**对每个歧义项**：
1. 标记原文引用（精确到章节/段落）
2. 解释**为什么**这是歧义（不只是说"措辞不好"）
3. 给出改写建议 或 提出澄清问题
4. 评估风险等级：🔴 高（阻塞测试设计）/ 🟡 中（影响覆盖）/ 🟢 低（可容忍）

**输出**：`歧义报告.md`

```markdown
## 歧义报告

| 编号 | 原文引用 | 歧义类型 | 风险 | 改写建议/澄清问题 | 状态 | 确认结论(业务填) |
|---|---|---|---|---|---|---|
| AMB-001 | "系统应及时处理" | 模糊时间 | 🔴 | "及时"是指实时、1分钟内、还是下一个工作日？ | 待确认 | ⬜ 及时=实时/1分钟/下一工作日? |
```

### Phase 3: 缺口审计（Gap Audit）

**目标**：审计需求集相对于工程完整性的缺失项。（来自 45ck/requirements-gap-auditor + requirements-interrogator）

**十二维度完整性检查矩阵**：

| # | 审计维度 | 检查项 |
|---|---|---|
| 1 | **角色与权限** | 每个功能是否明确了操作角色？未登录、越权、多角色冲突？ |
| 2 | **触发条件** | 每个流程是否有明确的触发入口？自动触发还是手动触发？ |
| 3 | **前置条件** | 操作前需要什么数据/状态/配置就绪？ |
| 4 | **主流程** | 正常流程是否步骤完整、有始有终？ |
| 5 | **异常流程** | 失败、超时、取消、中断时的处理？ |
| 6 | **数据规则** | 字段类型、长度、格式、必填/选填、唯一性、默认值？ |
| 7 | **状态流转** | 状态枚举完整吗？哪些操作触发状态变化？终态是什么？ |
| 8 | **安全与合规** | 数据加密、脱敏、审计日志、合规要求？ |
| 9 | **并发与时序** | 多人同时操作？操作顺序依赖？竞态条件？ |
| 10 | **错误处理** | 错误码、提示信息、回滚策略、重试机制？ |
| 11 | **运维与可观测** | 监控、告警、日志、配置变更、灰度发布？ |
| 12 | **生命周期** | 数据过期、归档、清理、迁移策略？ |

**对每个缺口**：标记为 `缺失`（完全没提）/ `薄弱`（提了但不充分）/ `延迟`（明确留到后续阶段），并建议填补方式。

**输出**：`缺口审计报告.md`

```markdown
## 缺口审计报告

| 编号 | 审计维度 | 功能模块 | 缺口类型 | 描述 | 建议填补方式 | 风险等级 | 确认结论(业务填) |
|---|---|---|---|---|---|---|---|
| GAP-001 | 异常流程 | 用户注册 | 缺失 | 未定义注册超时/网络中断的处理 | 向产品确认 | 🔴 | ⬜ 超时/中断处理=? |
```

### Phase 4: 垂直切片（Vertical Slicing）

**目标**：将需求拆分为可独立测试的功能切片，而非按技术层横向切割。（来自 addyosmani/planning-and-task-breakdown）

**依赖图绘制**（先画依赖再排顺序）：

```
用户认证/权限体系
│
├── 基础数据管理
│       │
│       ├── 核心业务模块 A
│       │       │
│       │       ├── 查询/统计模块
│       │       └── 审批/流转模块
│       │
│       └── 核心业务模块 B
│
└── 系统配置/参数管理
```

**垂直切片 vs 水平切片**：

❌ 水平切片（反模式）：
```
任务1：建完所有数据库表
任务2：写完所有 API
任务3：做完所有页面
```

✅ 垂直切片（推荐模式）：
```
切片1：用户可完成[功能A]的完整操作（数据+接口+页面）
切片2：用户可完成[功能B]的完整操作
切片3：管理员可完成[配置功能]的完整操作
```

**每个切片输出为独立模块文件**，包含：
1. 模块范围（包含/不包含）
2. 业务流程（含状态流转图）
3. 功能规则表（编号、内容、来源、证据等级）
4. 字段/状态/配置/权限
5. 异常与边界（已知部分）
6. 验收标准草案
7. 模块级风险小结

**切片粒度控制**（来自 addyosmani 任务粒度表）：

| 粒度 | 文件数 | 测试范围 | 示例 |
|---|---|---|---|
| XS | 1 | 单个配置项或规则 | 一条验证规则 |
| S | 1–2 | 一个功能点 | 新增/编辑一个实体 |
| M | 3–5 | 一个功能切片 | 完整的 CRUD + 状态流转 |
| L | 5–8 | 多组件功能 | 带筛选+分页+导出的查询 |
| XL | 8+ | **太大，继续拆分** | — |

**拆分判断规则**：
- 标题中出现了"和/与/及" → 大概率是两个切片
- 涉及两个以上独立子系统 → 需要拆分
- 验收标准超过 5 条 → 需要拆分
- 无法在一个测试会话中完成 → 需要拆分

### Phase 5: 边界与异常挖掘（Edge Case Mining）

**目标**：从正常需求中生成边界、无效、异常、罕见场景。（来自 45ck/edge-case-elicitor + testomatio/qa-thinking）

**八维边界生成矩阵**：

| 维度 | 生成方向 | 示例场景 |
|---|---|---|
| **数据边界** | 空值、超长、极值、±1、特殊字符、重复 | 名称输入 256 个字符 |
| **时序边界** | 过期、并发、顺序颠倒、超时、跨时区 | 审批人在审批期间被禁用 |
| **权限边界** | 未登录、越权、角色变更、多角色冲突 | A 创建的数据 B 能否编辑？ |
| **状态边界** | 非法状态转换、中间态操作、终态回退 | 已归档的数据能否重新编辑？ |
| **环境边界** | 浏览器兼容、网络中断、服务端超时、设备切换 | 提交过程中网络断开 |
| **批量边界** | 空批量、超大批量、部分成功、全部失败 | 批量导入 10000 条记录 |
| **配置边界** | 开关切换、阈值临界、配置缺失、热更新 | 审核规则从 2 级改为 1 级，已在途的怎么办？ |
| **集成边界** | 第三方超时、接口变更、数据格式异常 | 支付回调延迟 30 分钟 |

**质量门禁**：
- 每个边界场景必须可追溯到真实业务规则或工作流（不是凭空编造）
- 关键失败模式必须有代表
- 标记哪些需要需求澄清 vs 可直接作为测试点

### Phase 6: 质量门禁（Quality Gate）

**目标**：在基线锁定前做最终质量审查。（来自 45ck/quality-checks + testomatio/qa-requirement-reviewer）

**五项质量检查**：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | **可测试性** | 每条需求都能设计出可观察结果的验证方法 |
| 2 | **一致性** | 跨模块的规则、字段、状态定义无矛盾 |
| 3 | **完整性** | 12 维度审计无 🔴 级缺口遗留 |
| 4 | **歧义清零** | 所有 🔴 级歧义已解决或标记为"待确认" |
| 5 | **追溯性** | 每条功能规则可追溯到原文来源 |

**需求质量评分卡**：

```markdown
## 需求质量基线报告

| 维度 | 得分(0-5) | 说明 |
|---|---|---|
| 完整性 | ? | 12 维度覆盖率 |
| 清晰度 | ? | 歧义项数量与严重度 |
| 一致性 | ? | 跨模块冲突数 |
| 可测试性 | ? | 不可验证的需求占比 |
| 可追溯性 | ? | 有来源引用的规则占比 |
| **综合评分** | **?** | 加权平均 |

### 阻塞项清单（必须解决才能进入测试设计）
| 编号 | 类型 | 描述 | 影响模块 | 确认结论(业务填) |
|---|---|---|---|---|

### 待确认项清单（不阻塞但影响覆盖度）
| 编号 | 模块 | 问题 | 建议确认方式 | 确认结论(业务填) |
|---|---|---|---|---|
```

## 人在环路（HITL）确认列约定

> 目的：让业务/产品的确认结论**直接落盘到分析文档**。下游 `understand`/`design` 按 `glob("*.md")` 全量读取模块目录，只在对话里确认、不落盘则脚本读不到。

**凡带「待确认/风险/缺口/歧义」的表，产出时默认追加最后一列 `确认结论(业务填)`**，涉及：
- Phase 2 `歧义报告.md`（歧义清单表）
- Phase 3 `缺口审计报告.md`（十二维度审计表 + 空态专项表）
- Phase 6 `需求质量基线报告.md`（阻塞项清单 + 待确认项清单）
- 同目录若有 `analyze-requirements` 的 `风险清单与待确认汇总.md`，其风险表同样带此列

**占位符规则**：

| 标记 | 含义 | 用法 |
|---|---|---|
| `⬜` | 待填 | 🟡🟢 项、或无针对性问题的项，留占位 |
| `⬜ <针对性问句>` | 待填（🔴 预填） | 🔴/⚠️ 阻塞项预填"要拍板什么"的短问句，引导业务直接作答 |
| `✅ <结论>` | 已确认 | 业务填完把 `⬜` 换成 `✅` + 明确结论（结论 + 依据/范围） |

**生成时机**：Phase 2/3/6 产出文档时**默认就带列**（🔴 预填问句、其余 `⬜`），不要等业务确认后才补列。

**填写纪律**：
- 只在最后一格写，不动竖线与列数；答案里禁止出现竖线（会撑破表格），停顿用逗号/分号
- 一条结论对应一个编号；跨文档同一问题（如 AMB-001 = B-1 = 风险清单 CAT-Rx）结论必须一致
- 未确认项保持 `⬜`，下游据此标"待确认判据"，执行时记录"实现现状"而非直接判 FAIL

## 功能 vs 非功能分离检查

在 Phase 4 切片时，同步执行功能/非功能分类（来自 45ck/functional-vs-nonfunctional-splitter）：

| 分类 | 判断标准 | 处理方式 |
|---|---|---|
| 功能需求 | 系统必须执行的行为（CRUD、计算、通知） | 进入功能切片 |
| 非功能需求 | 质量属性（性能、安全、可用性、可靠性） | 进入非功能检查矩阵 |
| 业务规则 | 业务约束（审批层级、金额限制、时间窗口） | 进入规则表 |
| 外部约束 | 法规、平台限制、第三方依赖 | 进入约束清单 |
| 设计选择 | 实现方案（不是需求） | **标记并移出需求集** |

**常见误分类纠正**：
- "系统响应时间 < 2 秒" → 非功能（性能），不是功能
- "用户可以导出 Excel" → 功能
- "使用 Redis 缓存" → 设计选择，不是需求
- "遵守 GDPR" → 外部约束

## 需求审讯技巧（来自 45ck/requirements-interrogator）

对每条需求执行 **10 问审讯**：

| # | 审讯维度 | 核心问题 |
|---|---|---|
| 1 | 角色 | 谁执行此操作？不同角色有何差异？ |
| 2 | 触发 | 什么触发了这个流程？手动还是自动？ |
| 3 | 前置 | 操作前需要什么条件就绪？ |
| 4 | 主流程 | 正常路径的完整步骤是什么？ |
| 5 | 异常 | 失败/超时/取消/中断时怎么办？ |
| 6 | 数据 | 涉及哪些数据？格式、范围、约束？ |
| 7 | 策略 | 有无业务规则/计算逻辑/审批策略？ |
| 8 | 安全 | 权限控制？数据保护？审计要求？ |
| 9 | 时序 | 有无时间约束？过期？并发？顺序？ |
| 10 | 运维 | 如何监控？出故障如何处理？ |

**风险优先原则**：先审讯高风险需求（涉及资金、权限、状态流转、数据一致性的），再处理低风险需求。

## 递归分解策略（大规模需求）

当需求文档超过 50k 字或涉及 10+ 功能模块时，启用递归分解（来自 massimodeluisa/recursive-decomposition-skill）：

1. **先度量**：统计输入规模，决定是否分批
2. **先过滤后阅读**：用目录/标题/关键词定位，不逐字通读
3. **分批处理**：5–10 个功能模块为一批
4. **每批独立分析**：走完 Phase 1–5，产出独立文件
5. **合并验证**：交叉检查跨批次的一致性和冲突
6. **程序化综合**：带文件和章节引用，不凭记忆

## 输出目录约定

> 与 `analyze-requirements` 产物**同目录共存**（不覆盖、无文件名冲突）：六阶段分析文件与其拆分出的模块需求文件都放在 `output/02_split_requirements/{模块名}/`（本项目实际约定，非 `output/00_analysis/`）。

```
output/02_split_requirements/{模块名}/
├── 需求全景图.md              # Phase 1

```

## 常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| "边读边写" | 遗漏跨章节的冲突和依赖 | 先全局扫描，再逐模块深入 |
| "差不多就行" | 歧义潜伏到测试阶段才爆发 | 每个歧义必须有编号、有引用、有建议 |
| "替产品做决定" | 测试用例建立在错误假设上 | 标记"待确认"，不猜测 |
| "按技术层拆分" | 无法独立验证一个完整功能 | 垂直切片：每个切片端到端可测 |
| "一次性分析全部" | 上下文过载，遗漏细节 | 超大规模启用递归分解 |
| "只关注正向流程" | 异常和边界覆盖不足 | 八维边界矩阵强制扫描 |
