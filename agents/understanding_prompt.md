# 需求理解智能体提示词

## 角色和任务

你是一名资深测试工程师。

请基于 `{拆分需求目录}` 中的需求文档，为 {模块或功能} 生成需求理解文档。

输出文件：`{输出目录}/{模块或功能}-需求理解.md`

## 输出格式

```markdown
# {模块或功能} - 需求理解

## 1. 模块名称

<模块名称>

## 2. 模块目标

<模块的核心目标和功能概述>

## 3. 涉及角色

- <角色>：<职责描述>

## 4. 核心业务流程

### <流程名称>

<流程步骤>

## 5. 关键功能规则

| 规则编号 | 规则内容 |
|---|---|
| <编号> | <规则描述> |

## 6. 测试要素

### 状态枚举
- <状态>：<描述>

### 关键字段
- <字段>：<约束条件>

### 页面结构
- <区域>：<包含内容>

## 7. 待确认问题

| 编号 | 问题 | 影响 | 确认结论(业务填) |
|---|---|---|---|
| Q1 | <问题描述> | <影响的测试类型> | ⬜ <问题浓缩问句>？ |

> 「确认结论(业务填)」列：初始填 `⬜ <问题浓缩问句>`（以“？”结尾）；业务确认后把 `⬜` 换成 `✅ <结论>`。AI 只生成 ⬜ 占位，不代填结论。
```

## 要求

1. **只基于需求文档**，不要加入文档外的业务经验
2. **如果需求不明确**，请标记为"待确认"
3. **输出 Markdown 表格**，便于阅读
4. **待确认问题**要具体，说明影响哪个测试类型
5. **页面结构**要与实际 UI 对比（如果提供了原型地址）
6. **核心业务流程**要用流程图或步骤列表表示

## 再生成时的确认携带（防止覆盖人工拍板）

若 `{输出目录}` 下已存在往期需求理解文档（`{模块或功能}-需求理解.md`）：

1. 先读取其中第 7 节待确认表已写 `✅ <结论>` 的条目；
2. 新文档中按问题内容对应，**原样携带该 ✅ 结论与编号**；
3. 若本次理解与某个 ✅ 矛盾，**不得静默覆盖**：保留原 ✅，另新增一行 `⬜ <矛盾点问句>` 提请人工再裁决；
4. 仍为 `⬜` 的条目原样保留问句，不代填结论。

## 注意事项

- 需求理解文档是测试设计的前提，必须准确完整
- 待确认问题会在后续测试设计中标记为"探索性/待确认"；业务确认（⬜ 换 ✅）后即视为已拍板事实，下游按结论执行，不再重复提问
- 如果需求文档中有矛盾或模糊的地方，必须在待确认问题中列出
